# CLAUDE.md

T-Pot Sensor Deployer: a FastAPI web console plus an RQ worker that creates honeypot sensors in the cloud, configures them with Ansible, checks them, registers them with a local T-Pot CE **Hive**, publishes their IPs as a Palo Alto EDL feed, and rebuilds them on fresh IPs via "campaigns". README.md and docs/ describe the system; this file is what you need to change it safely.

## Design rules

- **The cloud API only creates and destroys machines** (and lists options). Everything after that is cloud-agnostic: SSH, Ansible (`playbooks/`), ping/TCP checks. Do not put sensor setup in cloud-specific code (no cloud-init user-data for DigitalOcean).
- **Never create a droplet you can't configure.** Preflight (playbooks exist, ansible and the key are present) runs before creation. Record the droplet and its TTL lease immediately after creating it, so failures can't leave an untracked billing machine.
- **SQLite is the only state store.** No JSON state files. Shapes belong in `app/models.py`.
- **No absolute host paths or `Path.home()`.** Everything derives from `DATA_DIR`, `TPOT_DIR`, `SECRETS_DIR` (`app/config.py`).
- **The Hive is live config.** Tests must never resolve to the real one (see Tests).

## Running it

Docker Compose is the only supported way (`web`, `worker`, `redis`). There is no bundled proxy: T-Pot's nginx routes `/sensors/` and `/edl/` to the web container (`nginx/tpot-location.conf`).

```bash
cp .env.example .env            # TPOT_HOST_DIR at minimum; secrets/ssh_key + ssh_key.pub
docker compose up -d --build    # code is baked into the image; rebuild after edits
docker compose logs -f web worker
```

- **Check the Tasks page (or `get_recent_tasks`) for running jobs before rebuilding.** Recreating the worker kills an in-flight deploy. On startup the worker marks tasks left `running`, and half-provisioned manual sensors, as failed (`reap_interrupted_tasks`, `db_fail_interrupted_provisioning`). It assumes a single worker.
- Code is **not** bind-mounted. All state is in the `deployer_data` volume at `/data`. `TPOT_HOST_DIR` is mounted at `/tpot` (read/write: Hive registration writes `data/nginx/conf/lswebpasswd` and `.env`). `SECRETS_HOST_DIR` (default `./secrets`) is mounted read-only at `/secrets` (`ssh_key`, `ssh_key.pub`, `gcp-sa.json`).
- `.env` reaches the containers through `env_file`, so host-only variables (`TPOT_HOST_DIR`, `SECRETS_HOST_DIR`, `PUID`, ...) must not share names with in-container ones (`TPOT_DIR`, `SECRETS_DIR`, `DATA_DIR`), which the compose `environment:` block pins.
- Containers run as `PUID:PGID` (+ group `TPOT_GID`). That uid has no `/etc/passwd` entry and OpenSSH refuses to run without one, so `docker-entrypoint.sh` adds one with libnss-wrapper. **`docker compose exec` bypasses the entrypoint**, so SSH tried by hand through `exec` fails; the app's own processes are fine.

## Layout

- `app/api.py`: routes and page routes. Templates in `app/templates/` extend `base.html`; one shared `app/static/js/app.js`.
- `app/models.py`: `Settings`, `Sensor`/`SensorStatus` (`provisioning`, `active`, `provision_failed`), API payloads.
- `app/config.py`: paths and settings. Settings go to the browser through `public_settings()` (masks `do_token`); never return raw settings.
- `app/db.py`: SQLite (WAL). Tables: `active_droplets`, `leases`, `schedules`, `static_ips`, `fleet_history`, `settings`, cloud option caches. Fleet reads never call the cloud API.
- `app/jobs.py`, `app/queue_manager.py`, `worker.py`: RQ jobs on Redis; `worker.py`'s `SchedulerThread` is the **only** place the campaign tick (10 s) and TTL sweep (60 s) run - `app/api.py`'s startup used to fall back to running its own copy of both loops whenever no RQ worker was registered *yet*, but `web` and `worker` start concurrently with no ordering between them, so `web` routinely won that race and ran a second, permanent copy of both loops with no real cross-process lock (every dispatch/teardown/TTL destroy could fire twice). Removed; the worker container is required, not an optional target to fall back from.
- `app/ansible_runner.py` (run a playbook: key copied to a 0600 temp file, secrets via a 0600 vars file), `app/provisioning.py` (`configure_and_verify`: pick SSH port, run the sensor playbook, health check with retries, wait for firewall admission), `app/health.py` (`quick_check`, `deep_check`). Both take `remote_ssh_user` (default `root`, DO): a GCP image doesn't allow root SSH, so the GCP deploy path passes `tpotadmin` instead - every playbook already runs with `become: true`, so this is the only change needed, not a per-cloud playbook branch. `ansible_runner.wait_for_ssh_auth` covers GCP's guest agent needing a few seconds after boot to actually install that user's key (a no-op wait for DO, where auth already works the instant the port opens).
- `app/scheduler_manager.py`: campaigns. Ticked every 10 s from `worker.py`. DigitalOcean cycle: `_dispatch_deploy` (preflight, deployer key, firewall, Hive login, bare droplet, `stage: waiting_ip`) -> `_reconcile_provisioning` (IP known: record the sensor as `provisioning` so the EDL lists it, spawn `_async_do_configure_worker`, `stage: configuring`) -> `_finalize_active` or `_abort_provisioning` (destroy droplet, drop Hive login, circuit breaker). The configure thread is handed everything up front because the spawning tick may not have saved state yet. The tick saves only schedules it touched; all instances share one process lock (meaningful again now that only one process ticks). `hive_token` lives in state until configured and is stripped from API output. Verified end-to-end against a real droplet: dispatch -> configure -> active -> single scheduled destroy -> cooldown, all exactly once.
- Both the manual deploy job (`run_do_deployment_job`) and campaign dispatch (`_dispatch_deploy`) must deregister the Hive login they just created if `create_droplet` then fails for any reason (bad name, DigitalOcean outage, quota). Only the campaign path did; the manual path left an orphaned login once, from a hand-typed name with an underscore during testing (the UI's own name field already replaces `_` with `-`, so this was a test artifact, not a UI bug - but the missing cleanup was real and is not name-specific). Both paths now match; see `test_manual_deploy_cleans_up_hive_login_on_create_failure` / `test_campaign_do_dispatch_is_bare_and_safe`.
- `app/hive_manager.py`: Hive detection, per-sensor logins (`sensor-<type>-<adj>-<noun>`), `lswebpasswd`/`.env` registration. `app/edl_manager.py`: the feed (lists `active` **and `provisioning`** sensors, so the firewall can admit a sensor while it is still being configured).
- `app/do_client.py`, `app/gcp_client.py`: cloud backends for manual deploys - create/destroy/list machines and options only, mirrored shapes (`app/cloud.py`'s `get_client(provider)` picks between them). GCP auth is `secrets/gcp-sa.json` via `GOOGLE_APPLICATION_CREDENTIALS`, not a token; a GCP instance addresses by *name* (not id) for every live call, unlike DO. GCP never assumes the project's auto-created "default" VPC exists (plenty of real projects don't have one - found live, the first real deploy attempt against this pipeline failed exactly this way): `ensure_sensor_network`/`ensure_network` create a dedicated `tpot-sensor-vpc` + one subnet per region on demand instead. That network is shared fleet infrastructure, not per-instance, so nothing destroys it when a single sensor is destroyed - `DELETE /api/gcp/network` (Admin page) is the manual teardown, and it refuses while any GCP sensor is still tracked.
- `app/gcp_manager.py`, `terraform/gcp/`, `app/provisioner.py`: legacy Terraform/cloud-init path. Fully orphaned now - neither manual GCP deploys nor GCP campaigns use it any more (both moved to `app/gcp_client.py` + Ansible). Kept in the repo only because `tests/test_multi_sensors.py` still exercises pieces of it (`GCPTerraformManager.list_workspaces`, `generate_cloud_init`, `build_sensor_compose_yaml`); safe to delete along with those test cases in a future pass if it's never going to be revived.
- `app/sensor_types.py`: sensor metadata (ports, catalog). `docs/` describes the rest.

## Playbooks (`playbooks/`)

A sensor type is supported when `sensors/<type>.yml` and `health/<type>.yml` exist; adding one is two small files (see `docs/PLAYBOOKS.md`). All 12 catalog types exist (`cowrie`, `dionaea`, `conpot`, `elasticpot`, `mailoney`, `heralding`, `ciscoasa`, `citrixhoneypot`, `redishoneypot`, `sentrypeer`, `adbhoney`, `multi_sensor`), each deployed on a real droplet and verified shipping events to the Hive before being trusted (`multi_sensor` needs `s-2vcpu-4gb`; the rest default to `s-1vcpu-2gb`). Things learned the hard way, all found only on real droplets:

- The `tpot` group (gid 2000) must exist before directories are owned by it.
- The SSH port move is two-phase (listen on 22 and the admin port, reconnect, then drop 22). Detect socket-activated sshd by `systemctl is-active ssh.socket`, **not** by the unit file existing (it exists on every Ubuntu 24.04). The packaged `ssh.socket` sets `BindIPv6Only=ipv6-only` and lists `0.0.0.0:PORT` and `[::]:PORT`; a bare `ListenStream=PORT` is IPv6-only. `ssh.socket.d` must be created.
- The sensor `.env` needs `TPOT_PERSISTENCE=on`, `TPOT_OSTYPE`, `TPOT_BLACKHOLE`, `TPOT_ATTACKMAP_*` or `tpotinit` refuses to start. `tests/test_multi_sensors.py` checks the template.
- **Logstash sizing.** T-Pot's stock sensor pipeline (`http_output.conf`) is one file for every honeypot; on a small machine it dies with `OutOfMemoryError: Java heap space` at startup, even at T-Pot's own 1 GB heap, and never ships. The deployer renders a trimmed per-sensor pipeline (`logstash_http_output.conf.j2`, own inputs/filters, no IP-reputation lookup) that starts at a 256 MB heap. Default: 512m heap, 1g limit, validated on a real 2 GB droplet (Logstash ~660 MB); the stock pipeline OOMs even on 4 GB. Docker still reports the container "healthy" during an OOM loop, so the health check waits for the pipeline and greps for the heap error.
- `MY_EXTIP`/`MY_INTIP` are written by `tpotinit` into `/data/tpot/etc/compose/elk_environment` and sourced by Logstash's entrypoint. `/data/hive.crt` must exist or the `http` output fails its config check.
- "Sensor can't reach the Hive" is a **warning**, not a failure: it depends on a firewall we don't control (a Palo Alto refreshing an EDL about every 5 minutes; it polls `/edl/sensors.txt` with an empty user agent, visible in T-Pot's nginx log).

T-Pot ships its own sensor pieces on the Hive at `/tpot`: `compose/tpot_services.yml` (every honeypot's definition), `compose/sensor.yml`, `compose/customizer.py`, `deploy.sh` and `installer/install/deploy.yml`. Our playbooks reimplement the sensor setup by hand; the login scheme in `hive_manager.py` mirrors `deploy.sh`. When adding sensor types, copy definitions from `tpot_services.yml` rather than inventing them.

## Frontend

- Under T-Pot nginx the app is served at `/sensors/`, directly at `/`. Use `getAppPath()`/`apiUrl()`; never hardcode absolute paths.
- `base.html` injects `app.js` dynamically, which does not hold up `DOMContentLoaded`. `app.js` inits immediately if the DOM is ready; page-inline scripts that call its helpers (e.g. `admin.html`) must wait for `window.addEventListener('load', ...)`.
- The SSE stream ends only on a **terminal** status (`completed`/`failed`). Raw Ansible output is `debug` level: terminal pane only, never the status headline.

- **UI conventions:** no colorful emoji (the single-color shield and rocket are fine). Sensor icons come from `sensorIcon()` (one Font Awesome glyph per type, set in `fetchSensorTypes`); text we don't control (backend log lines, task messages) goes through `plain()`, which strips emoji. Explanations go in tooltips (`data-tip="..."`, or the `tip-icon` question mark) and in `app/static/help.html`, not in paragraphs on the pages. Sensor cards and type dropdowns are rendered from `/api/sensor-types` (`renderSensorControls`); the API's `deployable` flag greys out types without playbooks, and `selectDeploySensorType` must refuse them before touching any state. Ports from the API are objects; format them with `portLabel()`.
- **Any free-text field a user can set** (a sensor/campaign/static-IP name, a comment) **must go through `escapeHtml()`** wherever it's interpolated into `innerHTML`/a template literal, full stop - nothing upstream sanitizes it (see Input validation & concurrency below). Never embed one inside an inline `onclick="fn('${x}')"` call, even escaped: escaping doesn't survive being decoded out of the HTML attribute and then treated as JS. Use a `data-*` attribute instead and read it back via `this.dataset.x` in the handler.
- **Theme:** the default look is dark; the one alternate, Pink Unicorn, is `app/static/theme-unicorn.css` (re-colours the Tailwind classes under `html[data-theme="unicorn"]`, toggled from Settings, saved in `localStorage.theme`, loaded before paint by a script in `<head>`). Emoji are allowed only there. `tests/ui_audit.js` audits the default theme.
- **Applying frontend-only changes without a restart:** templates and `app/static/` are read per request, so `docker cp app/templates/. tpot-deployer-web:/app/app/templates/` and `docker cp app/static/. tpot-deployer-web:/app/app/static/` update the UI live without touching the worker or scheduler. Python changes need a rebuild. Verify with `tests/ui_audit.js`.

## Tests

No pytest; each file is a runnable script and sets `DATA_DIR`, `TPOT_DIR` and `SECRETS_DIR` to temp dirs **before importing the app**, so it can never touch real state or the real Hive (an earlier version wrote 28 junk logins into the live Hive). Keep that header when adding tests.

```bash
python3 tests/test_sqlite_db.py
python3 tests/test_multi_sensors.py
python3 tests/test_gcp_client.py
```

`tests/test_worker_queue.py` needs a live Redis: `docker compose exec web python3 tests/test_worker_queue.py`. `tests/test_gcp_client.py` has no live GCP credentials to test against here, so it only covers request/response shaping against fake SDK objects and clean-failure-when-unconfigured - it does not prove `app/gcp_client.py`'s SDK calls are correct against the real API (their field/method names were hand-verified against an installed `google-cloud-compute` package instead). Unit tests cannot cover the playbooks' behavior on a real host: syntax-check them, render templates, exercise the SSH move in a systemd container (`jrei/systemd-ubuntu:24.04`), then **deploy a real test sensor with a short TTL** before trusting a change. Judge a Logstash test by its own `Pipeline started` line; grepping the log for `OutOfMemoryError` matches the JVM's startup flags.

## Known gaps

- Conpot deploys only the `default` ICS template (Modbus, S7, EtherNet/IP, BACnet, SNMP) via `conpot_default`, not the other three template containers T-Pot's compose ships (`IEC104`, `guardian_ast`, `kamstrup_382`); add them as separate services in `sensors/conpot.yml` if you need those protocols too.
- The local `tpotce` reference clone (used to generate playbooks and Logstash filters) is pinned at 24.04.0 (Oct 2024); upstream is at 24.04.1 and has added several honeypots since (Beelzebub, Galah, go-pot, h0neytr4p, honeyaml, miniprint, rdphoneypot). None of the 12 types above are affected, but adding a new type should start from a refreshed clone.
- **GCP manual deploys** now use create-then-Ansible (`app/gcp_client.py`) same as DO - fleet tracking, TTL leases, EDL, the trimmed Logstash pipeline, health checks, all shared code. Verified end to end against a real GCP project for **Cowrie only** (dedicated VPC/subnet creation, firewall, instance create, Ansible configure including the two-phase SSH port move, health checks all passing, EDL updated, destroy). The other 11 types are almost certainly fine (identical GCP-side code path, same playbooks DO already validated per-type) but haven't each been deployed on a real GCP instance the way they were on DO - do that before fully trusting a non-Cowrie GCP deploy. Three real bugs were found and fixed getting Cowrie working: `DeployPayload.image` defaulting to DO's slug and leaking into GCP requests (see `resolve_gcp_deploy_field`), no default GCP VPC network in a real project (now a dedicated `tpot-sensor-vpc` created on demand), and a `become` + non-root-SSH-user + shared `remote_tmp` collision in Ansible (fixed by dropping the `ANSIBLE_REMOTE_TEMP` override entirely and using Ansible's own per-user default).
- **GCP campaigns are now on the same create-then-Ansible pipeline as manual GCP deploys.** `_dispatch_deploy`'s GCP branch does preflight/firewall/Hive-registration inline, then hands off to `_async_gcp_provision_worker` (one background thread that creates the instance via `GCPClient.create_instance` - which already blocks until the instance exists with an IP, unlike DO's non-blocking create+poll - then runs `configure_and_verify(..., remote_ssh_user=GCP_SSH_USER)`, then joins the same "ready" wait-loop `_async_do_configure_worker` uses to hand off to `_finalize_active`/`_abort_provisioning`). `_reconcile_provisioning`'s `stage == "configuring"` / interrupted-worker-restart detection is now provider-agnostic (used to be gated `if provider == "digitalocean"`); only the droplet-ID-polling `waiting_ip` stage stays DO-only, since GCP never enters it. `_abort_provisioning` and `_execute_destroy` are provider-aware via `app.cloud.get_client` (`destroy_droplet(id)` for DO, `destroy_instance(name, zone)` for GCP - fixes the old no-op-for-GCP bug this section used to describe). `_finalize_active` now correctly sets `provider`/`region` on the `Sensor` row instead of always defaulting to `"digitalocean"`/`config["region"]` regardless of the schedule's actual provider (a real bug that only mattered once GCP campaigns existed for real). There's still no UI for GCP zone rotation the way DO has region rotation - the "Rotate regions" toggle is hidden/disabled when GCP is selected in the campaign modal.
- **Campaign droplets now get an independent TTL backstop lease** - the decision CLAUDE.md previously deferred ("needs a real decision, not a guess made overnight"). Five touchpoints in `app/scheduler_manager.py` (`_schedule_backstop_lease`/`_cancel_backstop_lease`): (1) scheduled for `PROVISIONING_TIMEOUT_MINUTES + 15` minutes the moment a droplet/instance exists (DO: `_reconcile_provisioning`'s waiting_ip→configuring transition; GCP: `_async_gcp_provision_worker` right after `create_instance`); (2) extended at `_finalize_active` to `active_duration_seconds + CAMPAIGN_BACKSTOP_BUFFER_SECONDS` (24h slack); (3) cancelled at `_execute_destroy`/`_abort_provisioning` via `db_delete_lease` directly (not `TTLManager.cancel_lease()`, which also writes a "Cancelled by User" `fleet_history` row - inaccurate for an automated teardown, and campaign teardowns don't write fleet_history today; not introducing that as a side effect); (4) extended further to `PAUSE_BACKSTOP_SECONDS` (30 days) on `pause_schedule` if the campaign is active with a droplet, so a brief pause can't get caught by the 24h buffer and strand-then-kill the sensor; (5) `resume_schedule` reality-checks a stored `status: "active"` against `db_get_active_droplet` before trusting it - if the droplet is actually gone (backstop fired while paused, or destroyed by hand from Fleet), it drops into `cooling_down` with a fresh `next_action_at` instead of resuming into a phantom active state with no destroy timer ever set again; otherwise it shrinks the lease back down from the 30-day pause extension to the normal target.
- `trigger_action` (the manual "Trigger now" button, called from the `web` container) claims the in-flight status under `_SCHEDULER_LOCK` before dispatching (see Input validation & concurrency below), which serializes concurrent calls *within* the `web` process. It still shares no lock with the 10 s tick in the separate `worker` process - only SQLite is common to both. A manual trigger landing in the same instant as the tick's own dispatch for the same schedule is a narrow, human-timed cross-process race, not the systemic every-request one that was here before; left as is.

## Input validation & concurrency (found by deliberately trying to break things)

A pass of adversarial testing - too-long and special-character input, concurrent requests, absurd values - found real bugs beyond the double-tick fix above. All fixed and regression-tested (`tests/test_sqlite_db.py::test_parse_duration_rejects_absurd_values`, `tests/test_multi_sensors.py::test_concurrent_trigger_does_not_double_dispatch`, `::test_manual_deploy_cleans_up_hive_login_on_create_failure`).

- **Stored XSS via any free-text name.** `app.js` interpolated `sensor_name`/`type_label`/droplet, GCP and campaign `name`/`description`, and `state.last_message` (which can itself carry a campaign's `name_prefix`) straight into `innerHTML`, and separately into `onclick="fn('${x}')"` attributes with only a `'`-escape (not `"`, so a value containing a bare `"` broke out of the attribute entirely). Proven live with a deploy named `<img src=x onerror=alert(document.domain)>`, stored via `/api/deploy` and rendered by the Tasks page with no server-side sanitization anywhere in the chain. Fixed: `escapeHtml()` now escapes `"` and `'` too (full entity escaping), all plain-text interpolations use it, and everywhere a name was embedded in an inline `onclick(...)` call it now goes through a `data-*` attribute + `this.dataset.x` instead (entity-escaping a value and then re-embedding it inside a nested `'...'` JS string literal does not compose - the browser HTML-decodes the attribute *before* treating it as JS, undoing the escaping that was protecting the JS string boundary). `tests/ui_audit.js` cannot catch this class of bug (it checks for emoji and console errors, not for injected live DOM nodes); it was found by hand.
- **Concurrent "Trigger now" clicks created one real droplet per click.** `trigger_action` read a schedule's status, released the lock, and only *then* dispatched - so several concurrent calls (a mashed or double-clicked button, or a retried request) all read the same pre-dispatch status, all passed the "already in-flight" check, and all dispatched. Found live: 5 concurrent calls created 5 real droplets for one schedule slot; the schedule can only remember one `current_droplet_id`, so the other 4 became untracked, un-leased orphans (destroyed by hand once found - see the campaign-droplets-get-no-TTL-lease gap above, which is exactly what let this go unnoticed by any safety net). Fixed: the status check and the claim that backs off a second caller now happen under one `_SCHEDULER_LOCK` acquisition, before the slow dispatch/destroy work begins.
- **No upper bound on `count`, on duration strings, or on a droplet ID path parameter.** `DeployPayload.count` had no ceiling (`run_do_deployment_job` only clamps a *low* count up to 1); `parse_duration` accepted any size of number (`datetime + timedelta(seconds=...)` raises an uncaught `OverflowError` for anything that would land past year 9999 - found live with a campaign's `active_duration`, which only surfaced the crash once the campaign actually tried to go active, after a real droplet had already been created and configured); and `droplet_id: int` path parameters had no bound (`sqlite3` raises `OverflowError: Python int too large to convert to SQLite INTEGER` for a huge one, an unhandled 500 instead of a clean 4xx). Fixed with `Field(ge=1, le=10)` on `count`, a 10-year ceiling in `parse_duration` (shared by TTL leases and campaign timings), and an `Annotated[int, Path(gt=0, le=9223372036854775807)]` (`DropletId`, SQLite's real ceiling) on every route that takes one.
- **A `_finalize_active` failure after a successful configure crashed the background thread** instead of aborting the cycle cleanly - it would still self-heal a tick later via the "interrupted configuration" path (built for a worker restart), but only after an unhandled traceback and a wasted extra tick. Now wrapped: any exception there is treated the same as a configure failure.
- Also bounded: `name`/`description`/static-IP `comment` fields with no `max_length`, which cost nothing to fix and closes a class of "wall of garbage in a log line or DB row" issues even though none of them crashed anything on their own.
- **Confirmed safe, not changed:** SQL-metacharacter, null-byte, and unicode/emoji names all round-tripped through the DB and task list without incident (every query in `app/db.py` is parameterized); an unknown `timing.mode` degrades to plain-interval behavior instead of crashing; `cooldown_min > cooldown_max` self-corrects in `_calculate_next_rebuild` instead of crashing `random.randint`; IPv6 static EDL entries are accepted (`is_valid_ip_or_cidr` isn't actually IPv4-only despite its error message saying so - harmless, just a stale message).
- The EDL feed is unauthenticated by design (the firewall polls it); its redesign is deferred.
- `doconsole-reference/` is a gitignored reference copy of an older project. Leave it alone.
