Help

What the deployer does, how the pieces fit, and what to do when something looks wrong.

Getting started

  1. Put your DigitalOcean API token in secrets/do_token on the deployer host: ./tpot-expansion-pack.sh asks for it. It can't be set from this UI.
  2. Open Admin. Click Verify token, then Sync options so the Deploy page has current regions and sizes.
  3. Open Deploy, pick a sensor type, choose an auto-destroy time (use 1 or 2 hours while testing), and click Launch sensor.
  4. Watch the progress dialog, or close it and follow the run on Tasks. A deploy takes about 5 minutes.
  5. When it finishes, the sensor appears on Fleet and its IP is in the firewall feed.

What a deploy does

The cloud provider is used only to create and delete the machine. Everything else happens over plain SSH, so it works the same way whatever the cloud.

  1. Checks first. It refuses to start if the sensor type can't be set up, so nothing is created and billed for nothing.
  2. Creates a login for the sensor in the Hive, so it can send its logs.
  3. Creates the machine with the deployer's SSH key, and records it straight away so it can never be forgotten.
  4. Publishes its IP to the firewall feed so the firewall can admit it while it is still being set up.
  5. Configures it: swap, Docker, the honeypot and log shipper, the Hive's certificate, and it moves admin SSH from port 22 to 64295 (the honeypot needs 22).
  6. Checks it: containers running, log shipper up, honeypot ports open, Hive reachable. If the firewall hasn't admitted it yet, it waits a few minutes.

If setup fails, the machine is kept for debugging (status provision failed) and is deleted when its auto-destroy time runs out.

Auto-destroy

Every sensor has a time limit, after which it is deleted along with its Hive login and its entry in the firewall feed. Set it when you deploy, and extend or remove it from Fleet (the + and x beside the timer). Choose Never only for a sensor you intend to keep and pay for.

Campaigns

Scanners such as Shodan and Censys record which addresses are honeypots. A campaign avoids leaving one in place: it runs a sensor for a window, destroys it, waits, then rebuilds it on a fresh IP address. Reserved and floating IPs are never used.

  • Fixed interval: rebuild after each cooldown. Random window: rebuild after a random cooldown so the pattern can't be predicted. Weekly: the same day and time each week.
  • Rotate regions moves to a different datacenter on each rebuild.
  • The worker checks campaigns every 10 seconds. It starts at most 3 rebuilds at once, and if a campaign fails 3 times in a row it is suspended to protect your account. Fix the cause, then resume it.

Firewall feed (Palo Alto EDL)

Sensors reach the Hive on port 64294 through your firewall. The firewall only admits addresses on a list, and the deployer keeps that list up to date as a plain-text feed (an External Dynamic List).

  1. In PAN-OS: Objects > External Dynamic Lists > Add. Type IP List, source = the URL on the EDL page, repeat every 5 minutes.
  2. Use that list as the source address of the security rule and the NAT rule that admit TCP 64294 to the Hive.

A sensor is listed as soon as it has an IP. The firewall picks the change up on its next refresh, usually within 5 to 7 minutes, and the deploy waits for that before it reports a warning.

Static entries are IPs added by hand. They are always in the feed, so check the list on the EDL page and remove any you don't recognise.

To confirm the firewall is fetching the feed, look at T-Pot's nginx log: requests for /edl/sensors.txt with an empty user agent, about every 5 to 7 minutes, come from the firewall.

Health and status

StatusMeaning
provisioningThe machine exists and is being set up. Its IP is already in the firewall feed.
activeSet up and passed its checks.
provision failedSetup failed. The machine is kept for debugging and deleted when its auto-destroy time runs out. The Tasks page has the log.

The Health button on Fleet does a quick ping and port check from the deployer. The full check (containers, log shipper, Hive reachability, disk) runs at deploy time.

"Cannot reach the Hive" is a warning, not a failure. The sensor is running and recording, but the firewall isn't admitting it yet, so its logs can't be shipped. See the firewall section.

Hive logins

Each sensor gets its own login in the Hive, so one sensor can be cut off without affecting the others. Admin lists them and marks each in use or not in fleet. A login that is not in the fleet is a leftover, for example from a machine deleted in the cloud console, and can be removed with its button.

Troubleshooting

What you seeWhat to do
"No DigitalOcean API token" bannersecrets/do_token is missing or empty on the deployer host. Run ./tpot-expansion-pack.sh --setup there, or write the token to that file. No restart needed.
Deploy fails straight awayOpen the task on Tasks and read the last lines. The most common cause is a missing SSH key file or an unsupported sensor type.
Setup fails with a timeout on port 64295The deployer can't reach the sensor's admin port. The cloud firewall allows it only from the Hive's IP, so the deployer's outgoing IP must match the Hive's address.
Sensor is active but no logs reach the HiveCheck, in order: is the log shipper running on the sensor; can the sensor reach the Hive on 64294; is the firewall admitting it (see above); does its login exist (Admin).
The Deploy page lists no regions or sizesAdmin, then Sync options.
A task says it was interruptedThe worker was restarted while it ran. The machine may still exist; check Fleet and delete it if you don't want it.
A campaign is suspendedIt failed 3 times in a row. Read the error on the Campaigns page, fix it, then resume.

You can reach a sensor from the Hive host with ssh -i secrets/ssh_key -p 64295 root@<sensor-ip>, then docker ps and docker logs logstash.

Glossary

Hive
: the central T-Pot install that receives and stores logs from all sensors.
Sensor
: a cloud machine running a honeypot and shipping its logs to the Hive.
Honeypot
: a fake service that records what attackers do to it.
EDL
: External Dynamic List, a text list of IPs a Palo Alto firewall re-reads on a schedule.
Auto-destroy (TTL)
: the time after which a sensor is deleted automatically.
Campaign
: a schedule that destroys and rebuilds a sensor on fresh IPs.
Playbook
: the Ansible script that sets up (or checks) one sensor type over SSH.
Worker
: the background process that runs deploys, destroys, campaign steps and expiry checks.
